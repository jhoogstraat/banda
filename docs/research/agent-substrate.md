# Agent Substrate vs agent-sandbox for Banda: research

Checked 2026-10-19. Primary sources only. Substrate links point at [`agent-substrate/substrate` tag `v0.5.0`](https://github.com/agent-substrate/substrate/tree/v0.5.0) (commit `e8d40c33`, 2026-10-14). agent-sandbox links point at `v1.0.7`, as in [sandbox-lifecycle.md](sandbox-lifecycle.md). I read the source of both from a local clone; I installed nothing and ran nothing.

## Summary

- **Recommendation: don't adopt now. Revisit later under the conditions below.** Substrate gives Banda one thing agent-sandbox can't: a running `claude` process (memory, TTY state, background jobs) survives a pause. Banda doesn't need that for v1, because `claude --resume` over the PVC already restores the conversation in about 3-10 s. And Substrate is a poor fit on three hard points: it is Linux-only and unproven on macOS Podman, it has no shared writable volume across actors, and it freezes `claude` mid-flight instead of stopping it with SIGTERM.
- **Maturity: v0.5.0 (2026-10-14), pre-1.0, five minor releases in 5 weeks, and the README says "no guarantees about backward compatibility"** ([README](https://github.com/agent-substrate/substrate/blob/v0.5.0/README.md#status-and-compatibility)). v0.5.0 lists 10 breaking changes ([release](https://github.com/agent-substrate/substrate/releases/tag/v0.5.0)). The [upgrade runbook](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/upgrade.md) says minor upgrades before 1.0 are unsupported: reinstall. agent-sandbox is `v1beta1` and ships weekly patch releases.
- **Wake-up by API call works.** `ResumeActor`, `PauseActor` and `SuspendActor` are plain gRPC RPCs ([ateapi.proto](https://github.com/agent-substrate/substrate/blob/v0.5.0/pkg/proto/ateapipb/ateapi.proto#L25-L70)); inbound HTTP through the router is only one trigger. So Banda's API could drive it with the same state machine it has today.
- **Four blockers for Banda today.** (1) The per-user Claude login volume can't be shared: volumes are per actor, and shared writable storage is listed under "ideas we are thinking about" ([roadmap](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/roadmap.md)). (2) Checkpointing freezes `claude` wherever it is, including in the middle of an OAuth refresh. A lost refresh response can log the user out, the exact failure the SIGTERM rule exists to prevent (inferred, unverified). (3) Egress is default-deny and goes through a gateway that blocks WebSocket and non-HTTP TCP; whether a long-lived Connect bidi stream and the Anthropic login endpoints work is unverified, and the Claude Code demo's own egress is broken ([#2487](https://github.com/agent-substrate/substrate/issues/2487)). (4) No documented path on macOS + rootful Podman; the dev scripts assume Docker and a Linux host.
- **Operating cost is much higher.** Substrate needs its own Postgres, S3/GCS-compatible object storage, an API server, a node DaemonSet, a router, an egress gateway and a pod-certificate controller, versus agent-sandbox's one controller. Open P1 wedge bug: actors stuck in `SUSPENDING` forever under traffic ([#1914](https://github.com/agent-substrate/substrate/issues/1914)).
- **Triggers to revisit** (any two): (a) a tagged `v1.0` or an API stability policy; (b) shared or per-user writable volumes across actors, or a documented way to keep `CLAUDE_CONFIG_DIR` consistent; (c) lifecycle hooks (PreSuspend/PostResume, [#450](https://github.com/agent-substrate/substrate/issues/450)) so the runner can stop `claude` gracefully before a checkpoint and restart it after; (d) a documented, tested kind-on-macOS (or Podman) path; (e) Banda needs processes to survive a pause (dev servers for the browser pane) or resume under a second, measured on real use; (f) Banda moves to a Linux cluster with ops capacity for Postgres and object storage. Also revisit if agent-sandbox adopts a snapshot provider ([#694](https://github.com/kubernetes-sigs/agent-sandbox/issues/694)), which would be the cheaper route to the same benefit.

## Side-by-side

| | agent-sandbox v1.0.7 (current) | Agent Substrate v0.5.0 |
|---|---|---|
| Maturity | SIG Apps, `v1beta1` CRDs, weekly releases, GKE Agent Sandbox GA is built on it | Pre-1.0 ("no guarantees about backward compatibility"), 6 tags in 5 months (v0.0.0 2026-05-19, v0.5.0 2026-10-14), 121 contributors, 19 listed maintainers (Google and Solo.io), ~830 open issues |
| Suspend / resume semantics | `operatingMode: Suspended` deletes the Pod and keeps the PVC; `Running` creates a new Pod from the current template | Actor `SUSPENDED` <-> `RUNNING` via RPCs. Pause = checkpoint to the node, pinned there. Suspend = checkpoint uploaded to object storage, actor unpinned. Resume restores onto any free worker |
| Resume latency | Pod start: about 3-10 s to first token (estimate, [sandbox-lifecycle.md](sandbox-lifecycle.md)) | README: "sub-500ms" at 500+ activations/s. Method unpublished. Not measured for a `claude` process. Unverified |
| What is preserved | Disk on the PVC only. Memory, processes and connections are lost | Selectable fidelity: `VOLUMES` (durable data only), `ROOTFS` (micro-VM only), `MEMORY` (processes resume where they were). Memory snapshots are tied to the template version and runtime version, and fall back to `VOLUMES` when no compatible worker exists |
| Runtime requirements | Any runtime, including plain runc. Optional `runtimeClassName` | gVisor (`runsc`) or Cloud Hypervisor micro-VM (needs `/dev/kvm`). **runc is not supported**. Linux server components only ([#2517](https://github.com/agent-substrate/substrate/issues/2517)) |
| Local dev on macOS + Podman | Works today (kind on rootful Podman, runc) | Documented only for Docker-in-VM (Lima, Colima, Docker Desktop) with gVisor, and Lima with KVM for micro-VMs. Podman applehv: no mention anywhere. Unverified |
| Storage / shared volumes | PVC per Sandbox via `volumeClaimTemplates`, plus any PVC you reference from the pod spec. Banda shares one per-user PVC across threads | `durableDir` (travels inside the snapshot tar, one per gVisor actor) and `externalVolumeTemplate` (CSI volume created per actor, lives and dies with the actor). No PVC objects. No sharing between actors. Size is set per template (`capacity`) |
| Wake trigger | Your code patches `operatingMode`. No auto-resume on traffic | RPC `ResumeActor`, or an inbound HTTP request through the router with header `ate-target-actor: <atespace>/<actor>`. Idle detection does not exist yet ([#483](https://github.com/agent-substrate/substrate/issues/483)) |
| Outbound-connection model | Plain pod networking. The runner's bidi stream to the API works as is | All TCP egress is redirected through `atunnel` to an egress gateway. HTTP/1.1 and HTTP/2 allowed under an explicit per-actor allow-list; WebSocket, CONNECT and other TCP blocked; DNS refused without a policy ([egress-traffic.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/egress-traffic.md)). Connections do not survive a restore (inferred, see below) |
| Terminal / exec | Banda's runner opens the PTY and streams it over its dial-out stream. No change needed | Same approach would work if egress allows the stream. Substrate has no exec or PTY of its own ([#185](https://github.com/agent-substrate/substrate/issues/185) open) |
| Credentials / login persistence | Per-user PVC at `CLAUDE_CONFIG_DIR`, shared across threads. Banda never reads it | Per-actor volume only. A login would live in one actor's volume. Sharing across threads would need the not-yet-existing shared storage, or one login per thread |
| Components to operate | 1 controller (`agent-sandbox-system`) | `ate-api-server`, `atelet` (DaemonSet), `ate-controller`, `atenet-router`, `atenet-egress`, pod-cert controller, Postgres, object storage, per-actor `ateom` worker pods |
| API surface | Kubernetes CRD; Go clientset `sigs.k8s.io/agent-sandbox/clients/k8s/clientset/versioned` (what Banda uses) | gRPC `Control` service (`CreateActor`, `ResumeActor`, `PauseActor`, `SuspendActor`, `RevertActor`, `DeleteActor`, ...) plus `WorkerPool` and `SandboxConfig` CRDs. Generated Go client at `pkg/proto/ateapipb`, used by the demos. Bearer-token auth |

## 1. Maturity

- **Releases:** v0.0.0 (2026-05-19), v0.1.0 (09-10), v0.2.0 (09-25), v0.3.0 (09-30), v0.4.0 (10-08), v0.5.0 (10-14). Roughly one minor release a week since September, each with breaking changes ([releases](https://github.com/agent-substrate/substrate/releases)).
- **Stability statement:** "Agent Substrate is pre-1.0. We are not making any guarantees about backward compatibility at this stage" ([README](https://github.com/agent-substrate/substrate/blob/v0.5.0/README.md#status-and-compatibility)). The architecture doc opens with "Much of this architecture is aspirational, and is not yet implemented!" ([architecture.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/architecture.md)). The API server is gRPC with proto-defined resources, and `WorkerPool` is `ate.dev/v1alpha1`.
- **v0.5.0 breaking changes** include the `SandboxConfig`, `SnapshotFidelity` and `WorkerPool.sandboxClasses` API reshapes, renaming `ContainerWakeupProbe`, and moving the health port ([release notes](https://github.com/agent-substrate/substrate/releases/tag/v0.5.0)).
- **Upgrades before 1.0 mean reinstall** ([upgrade.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/upgrade.md)). Worker rollout sends SIGTERM and gives actors 30 minutes to be suspended before SIGKILL.
- **People:** created 2026-05-13, launched 2026-05-20 ([Google blog](https://cloud.google.com/blog/products/containers-kubernetes/bringing-you-agent-sandbox-on-gke-and-agent-substrate)). 19 maintainers, 16 from Google and 3 from Solo.io ([MAINTAINERS.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/MAINTAINERS.md)). 121 GitHub contributors. Weekly community meeting. CONTRIBUTING says "the project is VERY young" and may not review changes outside the core focus.
- **Open issues relevant to Banda** (about 830 open in total; the repo's `prio/P0` list has 30 items, mostly observability and identity work):
  - [#1914](https://github.com/agent-substrate/substrate/issues/1914): traffic during suspend wedges actors in `SUSPENDING` forever, pinning workers. There is no reconciler over actors; recovery is manual `DeleteActor --any-state`.
  - [#1525](https://github.com/agent-substrate/substrate/issues/1525) (P0): the router's 10 s default route timeout cuts off long actor turns.
  - [#811](https://github.com/agent-substrate/substrate/issues/811): the first resume after a gVisor release bump fails on a cold node.
  - [#2487](https://github.com/agent-substrate/substrate/issues/2487): the Claude Code multiplex demo cannot reach the Anthropic API because egress is denied by default.
  - [#644](https://github.com/agent-substrate/substrate/issues/644): `ateclient` mints one 1-hour bearer token and never refreshes it. A long-lived Banda API client would hit this.
- **Roadmap** is explicit about gaps: actor lifecycle semantics ("what data is retained across which events, e.g. gVisor upgrade -> loss of memory snapshot"), S3 plugin, shared writable storage, GC of idle actors, worker autoscaling ([roadmap.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/roadmap.md)).

## 2. Model

Terms from the [glossary](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/glossary.md) and [resource model](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/resource-model.md):

- **Actor:** the unit of work (one Banda thread would be one). A record in Postgres, namespaced by **Atespace**. Created from an `ActorTemplate`.
- **ActorTemplate:** immutable blueprint: containers (image, command, args, env, wakeup probe), volumes, sandbox config, `snapshotConfig.storageLocation`, CPU/memory `limits`. Created through the gRPC API or `kubectl ate create actor-template`, not as a Kubernetes object. Creating one boots it and takes a **golden snapshot** (version 0); new actors start from it ([api-guide.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/api-guide.md)). Without a wakeup probe the builder waits about 20 s before snapshotting.
- **WorkerPool (CRD, `ate.dev/v1alpha1`):** N warm pods running `ateom-gvisor` or `ateom-microvm`. Many actors are multiplexed onto few workers; capacity is declared by pod limits. An actor occupies a worker only while `RUNNING`.
- **Snapshots:** one owner each (actor or tag). Pause keeps files on the node; suspend uploads them to object storage. An actor owns one snapshot at a time ([architecture.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/architecture.md)).
- **`durableDir`:** a directory on the rootfs that persists with the actor. gVisor allows one per actor; micro-VM allows several ([api-guide.md L105](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/api-guide.md)).
- **Router and ingress:** `atenet-router` is Envoy with `ext_proc`. A request carrying `ate-target-actor: <atespace>/<actor>` makes the router call `ResumeActor`, then open an mTLS CONNECT tunnel to the worker's `atunnel`, which forwards to the actor. Only HTTP(S) is reachable inbound ([architecture.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/architecture.md#networking-stack-atenet--atunnel)).
- **Control plane needs:** PostgreSQL ([postgres.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/postgres.md); bundled in the kind install, Cloud SQL on GKE) and an object store for snapshots: GCS or S3 through the `objectstore-plugin` sidecar. The kind overlay ships `rustfs` as S3 ([manifests/ate-install/kind](https://github.com/agent-substrate/substrate/tree/v0.5.0/manifests/ate-install/kind)). Without a bucket, nothing suspends.
- **Per-actor config:** container `env` lives in the template. There is no per-actor env on `CreateActor`. An actor can read its own name, atespace and UID from a `systemInfo` volume file ([proto](https://github.com/agent-substrate/substrate/blob/v0.5.0/pkg/proto/ateapipb/ateapi.proto#L1560-L1600)). So Banda's runner would learn its thread ID from that file and fetch the repo URL, branch and runner token from the API, instead of getting them as env vars.

## 3. Lifecycle

- **Create:** `CreateActor` registers the actor as `SUSPENDED` pointing at the template's golden snapshot. Nothing runs until the first resume.
- **Resume (`ResumeActor`):** claims a free worker, restores the snapshot, waits for the wakeup probe if one is defined, and sets `RUNNING`. It is a unary gRPC call and returns `resumed: false` if already running. The router calls the same RPC on inbound traffic. Resume can fail (`RESOURCE_EXHAUSTED`) when the pool is saturated; the router can park requests ([request-parking.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/request-parking.md)), but an RPC caller has to retry.
- **Pause / suspend:** `PauseActor` checkpoints to the worker's node and leaves the actor pinned there. `SuspendActor` checkpoints and uploads (or uploads an existing pause), frees the worker and unpins. Both are explicit calls. **Nothing suspends an idle actor today**; the caller must ([#483](https://github.com/agent-substrate/substrate/issues/483)). The same as Banda's current ticker.
- **Revert / delete:** `RevertActor` returns a crashed or running actor to its last durable snapshot. `DeleteActor` works only on suspended or crashed actors unless `any_state` is set.
- **What is preserved:** depends on fidelity. `MEMORY` keeps processes and RAM, plus disk, tied to the same template and runtime version. If the runtime version changed (for example a gVisor upgrade), the restore silently downgrades to `VOLUMES`, which is a cold boot with durable data ([api-guide.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/api-guide.md)). Banda would need to handle both outcomes, as a resume that looks like a fresh start.
- **Resume latency:** the README says "sub-500ms resume operations at over 500 suspend/resume activations per second". The roadmap calls the goal "sub-100ms". I found no published method, sandbox class, or memory size. The repo has a latency harness ([phase breakdown runbook](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/dev/suspend-resume-phase-breakdown.md), [benchmarking](https://github.com/agent-substrate/substrate/tree/v0.5.0/benchmarking)); [#1646](https://github.com/agent-substrate/substrate/issues/1646) notes restore time is dominated by heavy actors. Whether a Node-based `claude` process with a large heap restores in under a second is unverified. The suspend path also uploads the full memory image, so the cost grows with RSS.
- **Outbound long-lived connections:** unverified in Substrate's docs. What the docs do show:
  - Actor egress is TCP-redirected into `atunnel`, then an mTLS CONNECT tunnel to the egress gateway, which dials the origin. That path runs on the worker, not inside the actor.
  - gVisor checkpoints need the flag `--allow-connected-on-save` to checkpoint with live connections at all, and a note in [architecture.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/architecture.md) calls it a workaround for "a bug in networking resumption". [#1914](https://github.com/agent-substrate/substrate/issues/1914) says the flag is missing on restore, and traffic during suspend wedges actors.
  - After restore the actor may land on another worker, so the tunnel and the upstream connection are new. The actor's kernel still thinks the old connection is open.
  - Inference: Banda's runner would see a dead stream, not a clean close, and would have to reconnect. The Connect client already needs reconnect logic for API restarts. Banda would additionally need a keepalive/ping on the stream, since a half-dead socket is the likely failure.

## 4. Runtimes and local development

- **Runtimes:** gVisor `runsc` (default) and Cloud Hypervisor micro-VM (Kata). No runc: the worker's `ateom` is built around `runsc` checkpoint/restore or the VMM ([architecture.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/architecture.md#sandbox-classes)). Sandbox binaries come from a cluster-scoped `SandboxConfig`.
- **Platform:** server components are Linux-only; macOS is only the CLI ([#2517](https://github.com/agent-substrate/substrate/issues/2517)).
- **kind quickstart** ([README](https://github.com/agent-substrate/substrate/blob/v0.5.0/README.md#quickstart-development)): `hack/create-kind-cluster.sh` (kind plus a local registry, via the `docker` CLI), then `hack/install-ate-kind.sh --deploy-ate-system`, which installs Postgres, rustfs, and all Substrate components. It needs Go (it builds images with `ko`). The README states "kind (including macOS via the Docker VM)" is the intended path and "Without KVM the cluster still works for gVisor" ([create-kind-cluster.sh L74-L84](https://github.com/agent-substrate/substrate/blob/v0.5.0/hack/create-kind-cluster.sh)).
- **Micro-VM on macOS** needs KVM inside the Docker VM, documented for Lima on Apple Silicon ([microvm-local.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/dev/microvm-local.md)). Nested virtualization on Apple Silicon depends on the chip and VM manager. Unverified for Podman applehv.
- **Podman:** zero mentions in README, docs or scripts. kind supports a Podman provider, but the scripts call `docker` and bind-mount `/dev/kvm`. Rootful Podman might work with gVisor; unverified, and I did not try.
- **Not tested:** I did not stand up a cluster, per the brief.

## 5. Storage

- **Per actor, no sharing.** `externalVolumeTemplate` "provisions an external volume per actor; the volume lives only as long as the actor" ([proto L1497](https://github.com/agent-substrate/substrate/blob/v0.5.0/pkg/proto/ateapipb/ateapi.proto#L1497)). It needs a CSI driver registered through `CSIDriverConfig` and a privileged node DaemonSet ([csi-volumes.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/csi-volumes.md), [csi-deployment.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/csi-deployment.md)). Validated with NFS, block and hostpath only; FUSE storage has no code path ([#1746](https://github.com/agent-substrate/substrate/issues/1746)).
- **An NFS `StorageClass` still creates one volume per actor**, so it doesn't give a shared per-user login volume. The roadmap lists "Shared writeable storage across actors (e.g. an NFS volume)" under ideas, not planned work.
- **`durableDir`** is captured into the snapshot. It is limited to one per gVisor actor and travels through object storage on every suspend, so a 10Gi checkout would be uploaded and downloaded with each cycle. Size limits: none documented for `durableDir`; `capacity` is free-form for CSI volumes. Unverified.
- **Consequence for the per-user Claude login:** the login would be per thread (inside the thread's actor), or it would have to be copied between actors, which Banda is not allowed to do (Banda never reads that volume). That breaks PLAN.md's "log in once for all your threads".

## 6. Fit with Banda's constraints

- **`claude` frozen across a snapshot.** A `MEMORY` snapshot captures the process mid-instruction. On restore:
  - **Token refresh:** if the checkpoint lands during a refresh request, the refresh may have completed server-side (rotating the refresh token) while the response is lost to the dead connection. The binary then holds an invalid token and the user must log in again. This is the same failure a SIGKILL causes. Substrate has no hook to quiet `claude` first: PreSuspend/PostResume hooks are only a proposal ([#450](https://github.com/agent-substrate/substrate/issues/450)), and there is no restore extension point ([#1284](https://github.com/agent-substrate/substrate/issues/1284)). Mitigation Banda could build: the runner tells `claude` to stop (it can, because it owns the process) and suspends only at a quiet point. But then memory preservation buys nothing, since the process was stopped anyway.
  - **Clock jump:** a restored gVisor guest sees wall-clock time advanced by the downtime, or possibly stale time. For micro-VMs, Cloud Hypervisor 53+ advances the guest clock, and older versions leave it frozen ([guestclock.go](https://github.com/agent-substrate/substrate/blob/v0.5.0/cmd/ateom-microvm/internal/ch/guestclock.go)). For gVisor I found no statement. Unverified. Token expiry checks inside `claude` would depend on it.
  - **TCP connections:** see section 3. The Anthropic API connection and the runner stream both die on restore.
- **SIGTERM, never SIGKILL.** A Substrate checkpoint sends no signal at all, so there is no SIGKILL, which is good. But there is also no SIGTERM for `claude`: the process is frozen as is. Substrate does send SIGTERM to each actor container's main process when a worker is evicted, then SIGKILL after 30 minutes unless the actor was suspended ([api-guide.md L548](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/api-guide.md)). Banda's runner would be PID 1 of the actor and could forward it, as it does today.
- **Login via terminal (PTY).** The runner opens the PTY and streams it over its dial-out connection, so it needs no Substrate feature, provided egress allows the stream (WebSocket is blocked; Connect over HTTP/2 is allowed in principle, unverified).
- **Egress for the login flow:** default deny with DNS refused unless an `EgressPolicy` allows each hostname. Banda would have to allow `api.anthropic.com`, `claude.ai`, `console.anthropic.com`, GitHub and the Banda API at minimum, per actor ([#1324](https://github.com/agent-substrate/substrate/issues/1324): there is no default policy in the template). The upstream Claude Code demo is broken for exactly this reason ([#2487](https://github.com/agent-substrate/substrate/issues/2487)). Substrate's credential injection (header rewriting by an MITM proxy) would conflict with Banda's rule that Banda never intermediates credentials, so Banda must not use it.
- **Git checkout persistence.** Works via `durableDir` or CSI volume. With `MEMORY` fidelity the whole rootfs comes back too. The suspend upload size matters (see section 5).
- **Isolation.** Substrate's gVisor user-space kernel and default-deny egress are stronger than plain runc pods and address PLAN.md's open risk 5 (token exfiltration by a prompted agent) better, since egress can be allow-listed. agent-sandbox can also run gVisor (`runtimeClassName`) on a Linux cluster, and offers an optional managed NetworkPolicy, so the gap on isolation is smaller than it looks. Substrate's own security doc says several controls are still "In Progress" or "Future" ([security.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/security.md)).
- **Claude Code on Substrate exists as a demo**, using an API key and `claude --print`, not a subscription login ([demos/claude-code-multiplex](https://github.com/agent-substrate/substrate/tree/v0.5.0/demos/claude-code-multiplex)). kagent's Claude harness takes the same path (API keys only; see [sandbox-lifecycle.md](sandbox-lifecycle.md) section 2). Nobody has shown the interactive-subscription-login shape on Substrate.

## 7. Operational cost

Substrate install (from [manifests/ate-install](https://github.com/agent-substrate/substrate/tree/v0.5.0/manifests/ate-install) and [operator-install.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/operator-install.md)):

- `ate-api-server` (gRPC), `ate-controller` (WorkerPool reconciler), `atelet` (DaemonSet), `atenet-router`, `atenet-egress`, a pod-certificate controller (a polyfill for a Kubernetes feature, used for mTLS and Postgres auth), `SandboxConfig` and `CSIDriverConfig` CRDs.
- PostgreSQL with separate owner and read/write roles, and an object store with its credentials. Both are stateful services Banda would back up and upgrade.
- NetworkPolicies default-deny ingress to `ate-system`; any in-cluster API client must label its namespace `ate.dev/api-access=true`.
- Worker pods are warm and cost memory whether or not actors run. Pre-1.0 upgrades mean reinstall.
- Compare: agent-sandbox is one Deployment plus CRDs, and Banda already runs it. Postgres already exists for Banda, but Substrate wants its own schema and roles.
- Pays off only at high density. The headline benefit (10-30x oversubscription) matters for hundreds of idle agents, not an internal team's tens of threads.

## 8. API surface for Banda's API server

- **gRPC `Control` service** on `api.ate-system:443`. Resume, pause, suspend, revert and delete are one-call RPCs; the Go client types are in `pkg/proto/ateapipb` (the demos' dashboards use it, for example [claude-code-multiplex/ui](https://github.com/agent-substrate/substrate/tree/v0.5.0/demos/claude-code-multiplex/ui)). Requires a bearer token ([authentication.md](https://github.com/agent-substrate/substrate/blob/v0.5.0/docs/authentication.md)) that the shipped client mints once per hour and never refreshes ([#644](https://github.com/agent-substrate/substrate/issues/644)).
- **Go module stability:** importing `github.com/agent-substrate/substrate` pulls a large dependency set (the repo vendors dependencies) and breaking proto changes every minor release.
- **CRDs** are limited to infrastructure (`WorkerPool`, `SandboxConfig`, `CSIDriverConfig`). Actors are not Kubernetes objects, so `kubectl get` shows nothing; use `kubectl ate`.
- kagent forks Substrate (`kagent-dev/substrate v0.5.0-alpha2`) to keep pace with the churn, a sign of how unstable the API is ([sandbox-lifecycle.md](sandbox-lifecycle.md)).
