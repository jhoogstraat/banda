# Configuration

The API reads its settings from environment variables; in the cluster the chart sets them from its [values](../deploy/helm/banda/values.yaml) (`api.env` for anything without a value of its own). Deploying is in [deployment.md](deployment.md).

## Sign in

The cluster runs [Dex](https://dexidp.io), a local OIDC provider, reached through the web server at `/dex` (in the cluster, through the API: see [deployment.md](deployment.md)). Sign in as `alice`, `bob` or `carol` (`@example.com`) with the password `password`. `DEV_AUTH=1 mise run api` skips sign-in and trusts the `X-Banda-User` header instead (default user `dev`).

To use another OIDC provider, set these before `mise run api` (or when running `cmd/api`) and register `$PUBLIC_URL/auth/callback` as its redirect URI:

| Variable | Meaning |
|---|---|
| `OIDC_ISSUER` | Issuer URL, which serves `/.well-known/openid-configuration`. Enables sign-in. |
| `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | Client credentials. |
| `PUBLIC_URL` | Origin the browser uses, default `http://localhost:5173`. The GitHub App's flows return there too (`/github/app`, `/github/callback`, `/github/installed`), and GitLab's (`/gitlab/callback`), with or without OIDC. |
| `SESSION_SECRET` | Signs the session cookie. If empty, a random one is used and sessions end when the API restarts. |
| `OIDC_PROVIDER_NAME` | The provider's name on Banda's sign-in page ("Sign in with Okta"), default `SSO`. Chart: `oidc.providerName`. |

Signed out, any page goes to Banda's sign-in page (`/signin`), which sends you to the provider and back to that page. A failed sign-in returns there with the reason, and signing out lands there too. The bundled Dex wears Banda's look (the chart's `files/dex`: three templates and a theme over the image's own), and the theme picked in Settings: it is served on Banda's origin, so it reads the same browser storage.

Without `OIDC_ISSUER` the API only starts with `DEV_AUTH=1`. Other API settings: `DATABASE_URL`, `KUBE_CONTEXT` (the kubeconfig context of an API outside the cluster; empty, the default, is the current one; mise sets `kind-banda`), `SANDBOX_NAMESPACE`, `SANDBOX_IMAGE`, `RUNNER_API_URL`, `IDLE_SUSPEND_AFTER` (default `30m`, checked every `IDLE_SWEEP_EVERY`, default `1m`), `LOGIN_IDLE_AFTER` (default `10m`: login environments without a terminal), `DELETE_SETTLED_AFTER` (default `168h`: settled environments whose work is pushed), `DELETE_IDLE_AFTER` (default `720h`: suspended environments, settled or not, whose work was all on origin and whose thread had no activity that long; `0` never), `MAX_SUBTHREAD_DEPTH` (default `3`) and `MAX_AGENT_THREADS` (default `8`: agents' sub-threads, see [PLAN.md](../PLAN.md)), `OVERLAP_WINDOW` (default `168h`: how recently two threads must have changed for shared files to count as an overlap; `0` turns overlaps off), `SANDBOX_EGRESS_ALLOW` (comma-separated CIDRs sandboxes may reach besides the internet, such as production; see Sandbox isolation), `DEX_URL` (a bundled Dex, e.g. `http://dex.banda.svc:5556`, whose issuer is `$PUBLIC_URL/dex`: the API serves it at `/dex/` and reaches it there directly; the chart sets it), `FORGE_HOSTS` and `PULL_REQUEST_POLL` (see [usage.md](usage.md#github-and-gitlab)), `TEST_SUSPEND_PAUSE` (tests only: holds every suspend between the thread's status and its pod), `TEST_FORGE_URL` (tests only: a fake forge API in place of every forge's, on 127.0.0.1, ::1 or localhost, or the API doesn't start), `TEST_GITHUB_APP_SECRET` (tests only: the GitHub App's Secret instead of `banda-github-app`, for APIs side by side in one namespace; it must start with `banda-github-app`), `TEST_GITLAB_APP_SECRET` (tests only: the prefix of the GitLab applications' Secrets instead of `banda-gitlab-app-`, for APIs side by side in one namespace; it must start with `banda-gitlab-app`), `TEST_KEEPALIVE_EVERY` (tests only: how often server streams send a keepalive, default `25s`), `ADDR` (default `:8787`), `METRICS_ADDR` (Prometheus metrics at `/metrics` on a listener of their own, e.g. `:9090`; empty, the default, serves none; the chart sets `:9090`, see [deployment](deployment.md)), `WEB_DIR` (serve a web build), `WATCH_BUFFER` (default `256`: events a thread stream may lag behind before it catches up from the database; small for tests).

What each environment may take, as Kubernetes quantities (the chart's `sandboxes` values): `SANDBOX_CPU` (default `4`), `SANDBOX_MEMORY` (`8Gi`) and `SANDBOX_SCRATCH` (`10Gi`, disk outside the volumes) limit a thread's pod; `SANDBOX_HOME_SIZE` (`10Gi`) is its volume, the checkout and home directory; `LOGIN_CPU` (`1`), `LOGIN_MEMORY` (`1Gi`) and `LOGIN_SCRATCH` (`1Gi`) limit a login environment; `CLAUDE_VOLUME_SIZE` (`1Gi`) is each user's Claude Code config volume. Limits apply from each pod's next start, volume sizes only to volumes created afterwards. Requests stay small (50m CPU, 128Mi memory and scratch), so the limits can't go below them; a bad value stops the API with an error.

The Browser tab shows apps running in a thread's environment from a second origin: `PREVIEW_ADDR` (default `:8788`) is where the API serves it, `PREVIEW_URL` the URL browsers use for it, by default the host they reach Banda on with that port. Keep it on the same site as Banda (another port, or a sibling subdomain such as `preview.banda.example.com`): the preview signs in with a SameSite cookie. Previewed apps run code from the sandboxes on that site; outside a trusted LAN serve Banda over https (its cookies are then `__Host-`) with the preview on a sibling subdomain.

## Sandbox isolation

Sandboxes run the repo's code and the agent, so NetworkPolicies let them reach only DNS, the internet and the API (`deploy/helm/banda/templates/policies.yaml`), and Postgres and Dex take connections only from the API and from outside the cluster (their templates); the chart installs them, in dev through `mise run up`. An API on this machine (`mise run api`) must listen on a port in 8700–8999 for sandboxes in `banda` to reach it.

Private networks, such as production or a private git host, are closed too until `SANDBOX_EGRESS_ALLOW` lists them: comma-separated CIDRs (`10.20.0.0/16,10.30.1.5/32`; NetworkPolicies can't name hosts). The API applies them when it starts, as the NetworkPolicy `sandboxes-allow` in `SANDBOX_NAMESPACE` (set it in the Secret `banda-api` in the cluster); empty removes it, and a bad CIDR stops the API with an error. Postgres, Dex and the API in the cluster (except on its runner port) still refuse sandboxes inside an allowed range, and the Kubernetes API and kubelets refuse them without a token. Everything else in the range is open, so allow only what agents need: a range over the cluster's own networks opens its other pods and NodePorts, and in dev one over `host.containers.internal` (192.168.127.254) the host's ports, Postgres's among them. For a production Kubernetes cluster, keep it separate from Banda's: put a kubeconfig for it in a secret and allow its API server's address if that is private. Don't give sandboxes a service account in Banda's cluster.

For a shared deployment install the chart ([deployment.md](deployment.md)): no NodePorts, a generated Postgres password, never `api.devAuth`, a CNI that enforces NetworkPolicy, and your cluster's pod network in `podCIDR` instead of kind's (`10.244.0.0/16`). With the bundled Postgres the API connects as `banda_api`, which owns its database but isn't a superuser ([deployment.md](deployment.md#postgres)); with your own database, give it such a role too. See [PLAN.md](../PLAN.md), open risk 9.

## GitHub App

Set up from Settings ([usage.md](usage.md#the-github-app)); nothing to configure but `PUBLIC_URL`, which GitHub sends browsers back to, and `FORGE_HOSTS` for a GitHub Enterprise Server. Its keys are in the Secret `banda-github-app` in `SANDBOX_NAMESPACE`, users' tokens in `banda-forge-<hash>` there: the API reads, writes and deletes them (the chart's Role), no pod mounts them. To make the app by hand instead, see [deployment.md](deployment.md#github-app).

## GitLab application

Set up from Settings ([usage.md](usage.md#gitlab)), one per GitLab host: gitlab.com, and self-hosted ones named in `FORGE_HOSTS` as `gitlab`. Nothing to configure but `PUBLIC_URL`, whose `/gitlab/callback` is the application's Redirect URI. Its ID and secret are in the Secret `banda-gitlab-app-<host>` (a `host:port` from `FORGE_HOSTS` as `<host>-<port>`) in `SANDBOX_NAMESPACE`, users' tokens of both grants in their `banda-forge-<hash>` there: only the API reads them, no pod mounts them. To make it by hand instead, see [deployment.md](deployment.md#gitlab-application). Postgres keeps who set it up, and every set up, replace and remove (`gitlab_app_changes`), which Settings shows.

`FORGE_HOSTS` names self-hosted forges as `host=github` or `host=gitlab`, comma-separated. A forge on a port other than its scheme's default is named with it (`git.corp.example:8443=gitlab`): a repository URL with a non-default port is a known forge only under that exact `host:port`, never as the bare host's or as github.com's or gitlab.com's, so no forge token or git credential goes to another server on the same host.

## Workload identity

Banda is an OIDC issuer of short-lived identity tokens for each running thread, as GitHub Actions is for its jobs: a secret manager or cloud that trusts Banda gives a thread's agent access as its owner, so the team fetches secrets at run time instead of pasting long-lived credentials into Settings ([PLAN.md](../PLAN.md), "Workload identity"). It needs no setting of its own:

- **Issuer** `PUBLIC_URL` without a trailing slash. Discovery is at `$PUBLIC_URL/.well-known/openid-configuration` and the public keys at `$PUBLIC_URL/.well-known/jwks.json`, unauthenticated (the dev server proxies them, the chart's ingress routes them to the API). Cloud providers require https with a valid certificate; a vault on the team's network can trust plain http, or the keys themselves.
- **Keys** RS256 (RSA-2048) in the Secret `banda-identity` in `SANDBOX_NAMESPACE`, created on the API's first start; rotation is in [deployment.md](deployment.md#rotating-the-identity-keys).
- **Audiences** are a team setting: **Settings › Workload identity**. None means off. Each audience's token is in every running thread at `/run/banda/id-tokens/<audience>` (the scheme dropped, characters other than letters, digits, `.`, `_` and `-` as `_`; Settings shows each path), in memory, refreshed every 5 minutes and within seconds of a change; `BANDA_ID_TOKEN_DIR` names the directory. Login environments get none.
- **Claims** `iss`, `aud`, `sub` (`user:<owner's sign-in email>`), `iat`, `nbf`, `exp` (15 minutes), `jti`, `email`, `email_verified` (always `true`), `thread`, `repo` (`github.com/acme/api`, with a non-default port `git.example:2222/acme/api`; empty without a repository, for a local `file://` one and for anything with other characters than letters, digits and `._/-`) and `branch`. After a handoff the next token names the new owner.
- **Whom tokens name.** The owner's sign-in email, only if the identity provider vouched for it and no other Banda user signed in with the same one: an `email_verified` claim of `false` at sign-in, or a shared email, gets no tokens, and the thread's chat says why. A provider that sends no `email_verified` (Entra ID) is trusted, as Kubernetes does. A user signed in without an email (dev auth) gets no tokens either.
- **Bind policies to `aud` and `sub` or `email`**, and `email_verified` where the target can. `repo` and `branch` only narrow: they are what the thread was created with, and anyone signed in can create a thread naming any repository, so a policy on `repo` alone admits every teammate. Every recipe below binds the person.

Settings has the recipes below with this Banda's issuer, an audience, its token path, a repository and your email filled in, and a copy button on each step. Only the token itself is verified end to end (the e2e suite checks the signature against the JWKS, the Go tests verify with go-oidc as a relying party would); **none of the recipes has run against the real system yet**.

| Target | How it trusts Banda | In the thread |
|---|---|---|
| OpenBao / Vault | `bao auth enable jwt`, `auth/jwt/config` with `oidc_discovery_url` and `bound_issuer` (or `jwt_validation_pubkeys`, the PEM keys Settings shows, when the vault can't reach Banda or the issuer is plain http, where discovery would let anyone on the path swap the keys), a role with `bound_audiences`, `user_claim=email` and `bound_claims` on `email_verified` and `repo`, and a policy templated on the entity alias (the email) so each person reads their own path | `bao write auth/jwt/login role=banda jwt=@/run/banda/id-tokens/<audience>`; `BAO_ADDR` as a team secret |
| Infisical | A machine identity with OIDC Auth: discovery URL and issuer `PUBLIC_URL`, subject `user:<email>`, the audience, optionally the `repo` claim | `infisical login --method=oidc-auth --machine-identity-id=… --jwt="$(cat <file>)"` (`--oidc-jwt` is the deprecated name) |
| AWS | An IAM OIDC provider for the issuer with the audience as client ID, a role whose trust policy checks `<host>:aud` and `<host>:sub`, and an inline policy as narrow as the work (the recipe: `secretsmanager:GetSecretValue` on `secret:users/<email>/*` and `secret:team/*`) | `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE=<file>` as personal secrets: the SDKs and CLI refresh by themselves |
| Google Cloud | A Workload Identity Federation pool and OIDC provider (issuer, allowed audience, `google.subject=assertion.sub`, an attribute condition on `email_verified` and `repo`), `secretAccessor` on single secrets (not the project) for `principal://…/subject/user:<email>`, or `principalSet://…/banda/*` for a team secret | A credential config file with `--credential-source-file=<file>`: no secret in it, but keep it out of the repository. Its content as the team secret `GOOGLE_CREDENTIAL_CONFIG`, written to `~/.config/banda/gcp.json` by `.banda/setup.sh`, and `GOOGLE_APPLICATION_CREDENTIALS` pointing there as a team secret |
| Kubernetes | Structured authentication (`--authentication-config`, 1.30+): the issuer, the audience, username from `email` with the prefix `banda:`, validation rules on `email_verified` and `repo`; RBAC on `banda:<email>` | A kubeconfig with `tokenFile: <file>`, kept out of the repository the same way: the team secret `BANDA_KUBECONFIG`, written to `~/.config/banda/kubeconfig` by `.banda/setup.sh`, and `KUBECONFIG` pointing there |

Tokens are readable by the agent in the pod, which acts for its owner; so is whatever they fetch. See [PLAN.md](../PLAN.md), open risk 5, for what this protects against and what not.
